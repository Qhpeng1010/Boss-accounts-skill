# 老板管账页面交互与验收规则

## 信息优先级

**BL-INT-001** `information-hierarchy`（信息层级） 按任务依赖关系排列信息：页面上下文、必要摘要、查询或输入、主要结果、行级或后续操作、补充说明。统计和装饰不得把主要任务挤出首个有效视口。

**BL-INT-002** `operation-scope`（操作作用范围） 查询操作属于查询表单，结果工具属于结果模块，行操作只作用于当前记录；未选中记录前，批量操作不可用。

## 查询与上下文

**BL-INT-003** `query-state-management`（查询状态管理） 查询应应用明确的用户条件，并正确重置分页；重置应恢复声明的默认值、清除临时勾选并返回可预期的数据集。查询区存在日期范围时，只有首个日期范围且未声明 `showPresets: false` 才在业务未声明其他默认周期时重置为“今日”；选择日期快捷项只更新这一项 `DatePicker.RangePicker` 的查询条件，由用户通过“查询”统一提交，且当前范围对应的唯一快捷项显示为选中态。首个日期范围已关闭快捷项以及所有后续日期范围均不产生快捷项，重置时恢复其声明初值或清空。展开/收起必须保留已输入的值，并按当前容器内条件与操作的实际排版行数决定是否出现：不超过两行时不显示；超过两行时显示。已经明确主次条件时，初始状态展示主条件和两行范围，其余条件收起；未明确主次条件时，初始状态完整展示，允许用户主动收起，不能由系统擅自隐藏条件。容器宽度变化时可以重新计算条件布局，但重算期间条件与已输入值必须持续可见，不得留下占位空白区。

**BL-INT-004** `context-preservation`（上下文保持） 分页、排序、列设置、Drawer 查看和可恢复的失败状态应尽量保留当前列表上下文。关闭 Drawer 或 Modal 不能悄悄重置来源列表。

## 表单与工作流

**BL-INT-005** `form-validation`（表单校验） 提交应就近校验必填、格式、范围、依赖和权限。隐藏后失效的下游值必须清除，除非业务明确要求保留。

**BL-INT-006** `submission-outcome`（提交结果） 提交必须防止重复执行。失败时保留用户输入并说明恢复方式；成功时给出明确业务结果：关闭并刷新、返回来源、留在当前页继续新增、打开详情或进入结果反馈。

**BL-INT-007** `workflow-progression`（工作流推进） 未通过前置条件不得进入下一步；返回上一步应保留有效输入；最终复核应只读，除非用户主动返回编辑。

**BL-INT-016** `simple-form-actions`（简单表单操作区） 独立简单表单页和带引导的简单表单，其操作区紧随最后一个字段，并与输入控件的起始线对齐；主按钮在前、辅助按钮在后，按钮之间保持 `16px` 间距，不使用底部操作栏。分组表单和步骤流程的操作区固定在 Shell 工作区最底部，覆盖 Footer 且不占用表单内容区；操作区高度为 `48px`，必须保留白色不透明表面与顶部浅灰分割线。全页表单的滚动内容末尾必须额外保留 `64px` 安全区，确保最后一个业务组和字段能够完整滚动到操作栏上方；最后一个字段本身不能因组件默认底部外边距产生多余留白。

**BL-INT-017** `result-follow-up`（结果后续操作） 结果页的主操作必须引导用户回到来源、继续处理或查看后续记录，不能只提供无意义的关闭操作。结果信息区在操作之前；反馈为可选、非阻断操作，选择后只反馈确认，不改变结果状态或主操作可用性。

## 状态、权限与风险

**BL-INT-008** `page-state-recovery`（页面状态恢复） Loading、首次空数据、查询无结果、请求错误、无权限和缺少前置条件是不同状态，必须使用不同文案和恢复方式。

**BL-INT-009** `state-permission-consistency`（状态与权限一致性） 可见操作必须与记录状态一致，未知状态不能按正常状态处理。页面、字段和操作权限分别表达；前端的显示与隐藏不替代服务端授权。

**BL-INT-010** `dangerous-action-confirmation`（危险操作确认） 危险或敏感操作确认前必须说明对象、影响范围、金额或数量（如适用）、是否可撤销和操作后的状态。所有 Modal 与二次确认弹窗均在视口内垂直居中，高风险资金或身份操作可能需要强于确认弹窗的验证方式。

**BL-INT-015** `dashboard-scope-consistency`（概览范围一致性） Dashboard 的数据范围控件必须同时作用于全部指标和图表；页面首屏优先展示范围、核心指标和最重要趋势，分布与排行作为同一监控任务的补充。Dashboard 不得借用查询条件、结果表格或分页来承载逐条业务操作。

## 验收模型

**BL-INT-011** `acceptance-evidence`（验收证据） 每条硬规则至少由一个明确场景验收。静态预检只证明规则、Page Spec、派生产物和固定运行时一致，不能替代视觉或交互验收；`review.md` 必须记录人工查看的预览、执行场景、观察结果和确认状态。未获得人工确认时，不得宣称已验证视觉或运行时行为。

## 交付门禁

**BL-INT-012** `delivery-gates`（交付门禁） Page Spec 交付必须同时通过以下静态检查，并提交预览供人工验收：

1. 导演规则、策略、Schema、渲染器和 Shell 的哈希与发布清单一致。
2. Page Spec 的 Schema 和语义能力校验通过。
3. 生成文件与 Page Spec 及固定渲染器输入完全一致。
4. 固定 Shell 和系统资产检查通过。
5. 必需的中文文案、状态和已声明交互均存在于规格与派生预览源码。
6. `preview.html` 可供人工查看，`review.md` 明确列出待验收场景；人工确认结果由验收者记录，不由浏览器自动化代替。

**BL-INT-013** `delivery-blocking`（交付阻断） 任一门禁失败即阻止交付，不存在“带备注通过”。能力缺口必须报告为不支持，不能记录为成功页面。

## 反馈与规则变更

**BL-INT-014** `feedback-change-routing`（反馈变更归属） 需求专属反馈优先修改 Page Spec；重复出现或具有通用性的反馈，应修改导演规则、策略、契约或渲染器，并补充回归覆盖。生成的 HTML、JavaScript 和 CSS 绝不是长期修复位置。
